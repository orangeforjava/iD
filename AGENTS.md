# Agents Guide for iD

This document provides context for AI coding agents (GitHub Copilot, etc.) working on the iD codebase.

## Project Overview

iD is a JavaScript-based editor for [OpenStreetMap](https://www.openstreetmap.org/) (OSM). It runs in the browser and uses **d3.js** for rendering map data as SVG elements. The codebase is written in modular ES6 with no external UI framework—all DOM manipulation is done via d3 selections.

## Architecture Overview

iD uses an **immutable data model** with an event-driven UI. The key architectural principle is that all map data (entities, graphs) is immutable—edits produce new copies rather than mutating in place.

### Data Flow

```
User Interaction → Mode → Operation → Action → Graph (immutable)
                                                  ↓
                                          History (undo/redo stack)
                                                  ↓
                                          Renderer → SVG DOM
```

### Key Architectural Concepts

- **Entities** (`osmNode`, `osmWay`, `osmRelation`) are **immutable** OSM data objects. Updates return new copies via `entity.update({...})`.
- **Graph** (`coreGraph`) is an immutable mapping of entity IDs to entities. Adding/replacing/removing entities returns a new graph.
- **History** (`coreHistory`) maintains an undo/redo stack of graph snapshots. The top of the stack is the current editing state.
- **Actions** are pure functions: `(graph) => newGraph`. They transform the data model.
- **Operations** wrap actions with UI context (tooltips, key bindings, availability/disabled logic).
- **Modes** are state machines with `enter()` / `exit()` lifecycle methods (Browse, Select, Draw).
- **Behaviors** are reusable interaction handlers installed/uninstalled by modes (Hover, Drag, Lasso).
- **Context** (`coreContext`) is the central dependency container providing access to history, map, services, and UI.

### Entity IDs

OSM entities are prefixed with their type letter for internal uniqueness:
- Node `123456` → `n123456`
- Way `123456` → `w123456`
- Relation `123456` → `r123456`

New (unsaved) entities use negative numeric IDs (e.g., `n-1`, `w-2`).

## Code Patterns

### Actions (Pure Graph Transformers)

Actions are higher-order functions that accept configuration and return a function `(graph) => newGraph`:

```js
// Simple action
export function actionAddEntity(entity) {
  return function(graph) {
    return graph.replace(entity);
  };
}

// Complex action with cascading effects
export function actionDeleteNode(nodeId) {
  var action = function(graph) {
    var node = graph.entity(nodeId);
    // Remove from parent ways, handle degenerate ways...
    return graph.remove(node);
  };
  return action;
}
```

### Operations (Action + UI)

Operations wrap actions and provide UI metadata:

```js
export function operationSplit(context, selectedIDs) {
  var operation = function() {
    var difference = context.perform(action, operation.annotation());
    context.enter(modeSelect(context, newIDs));
  };
  operation.available = function() { /* can it run? */ };
  operation.disabled = function() { /* why can't it run? */ };
  operation.annotation = function() { /* user-facing label */ };
  return operation;
}
```

### Modes (State Machines)

Modes define editor states with lifecycle hooks:

```js
export function modeBrowse(context) {
  var mode = { id: 'browse', button: 'browse' };
  mode.enter = function() { behaviors.forEach(context.install); };
  mode.exit = function() { behaviors.forEach(context.uninstall); };
  return mode;
}
```

### Validations (Data Quality Rules)

Validations check entities against quality rules:

```js
export function validationCloseNodes(context) {
  var validation = function(entity, graph) {
    // Check entity, return array of validationIssue objects
    return issues;
  };
  return validation;
}
```

### UI Components (d3 Reusable Pattern)

UI components follow the d3 reusable component pattern:

```js
export function uiComponent(context) {
  function render(selection) {
    // Use d3 enter/update/exit pattern
    selection.selectAll('.item')
      .data(items)
      .enter().append('div').attr('class', 'item');
  }
  return render;
}
// Usage: d3.select('#container').call(uiComponent(context));
```

### Services (Singletons with Caching)

Services manage external API communication with module-level state:

```js
var _cache = { loaded: {}, inflight: {}, rtree: new RBush() };
var dispatch = d3_dispatch('loaded', 'change');

export default {
  init: function() { /* ... */ },
  loadTiles: function(projection) { /* ... */ },
  reset: function() { _cache = { /* ... */ }; }
};
```

### Event System

iD uses `d3-dispatch` for the Observer pattern. Events are dispatched and listened to:

```js
var dispatch = d3_dispatch('change', 'merge');
dispatch.call('change', this, difference);
// Listening:
history.on('change', function(difference) { /* react */ });
```

## Coding Conventions

- **ES6 modules** with `export function` / `export default`
- **2-space indentation** for ES6 files (4-space for legacy ES5 files)
- **Single quotes** for strings
- **Semicolons** always required
- **No `new` keyword** for most classes (factory function pattern), except for performance-critical classes (`coreGraph`, `osmEntity` subclasses) which use the instanceof trick
- **Immutability** — never mutate entities or graphs in place
- **Functional style** — actions are pure functions, use closures for encapsulation
- **Fluent API** — many methods return `this` or the parent object for chaining
- All code must pass **ESLint** with no warnings
- Complexity limit: **50** (ESLint warning threshold)
- Naming: module prefix matches directory (e.g., `actionDeleteNode` in `actions/`, `osmNode` in `osm/`)

## Build System

## Common Pitfalls

1. **Never mutate entities.** Always use `.update()` or action functions to produce new copies. In debug/test mode, entities are frozen with `Object.freeze`.
2. **Graph operations return new graphs.** `graph.replace(entity)` does not change the original graph.
3. **Entity IDs are prefixed strings** (`n123`, `w456`, `r789`), not raw numbers.
4. **Services are singletons** with module-level state. They must be `reset()` between test runs or context switches.
5. **d3 selections** are the primary DOM API — there is no React, Vue, or Angular.
6. **CSS classes are tag-derived.** Entity tags like `highway=residential` become CSS classes `tag-highway tag-highway-residential`.
7. **Actions must handle cascading effects.** Deleting a node must also clean up parent ways and relations.
8. **`context`** is threaded through most functions. It provides access to history, map, services, presets, etc.
